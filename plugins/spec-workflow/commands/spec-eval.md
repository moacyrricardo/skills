Deeply evaluate the work done on the current branch against the spec. Read-only — no file changes, just a thorough written evaluation.

---

## Step 1 — Orient yourself

1. Identify the current branch: `git branch --show-current`
2. Find the corresponding `doing` spec in `specs/` (match by branch name or ask the user if ambiguous). Read it fully — its structure, and the meaning of *spec* vs *concern*, follow the `spec-conventions` skill.
3. Get the full diff of what was built: `git diff main...HEAD` (or `git diff origin/main...HEAD` if needed).
4. Read every changed file in full — not just the diff hunks. You need full context to evaluate properly.
5. Read the project's `CONTRIBUTING.md` if present — it is the authority for how commits and PRs divide a change (you measure the branch against it in axis D). If the project has no `CONTRIBUTING.md`, note that the change-division rules are unwritten and skip axis D.

---

## Step 2 — Load or bootstrap the project architecture

Check whether `ARCH.md` exists in the project root.

### If `ARCH.md` exists

Read it. That document is the architecture benchmark for the evaluation. Skip to Step 3.

### If `ARCH.md` does NOT exist — bootstrap it

The project has no recorded architecture. Run the bootstrap process now — before evaluating anything.

**2a. Explore the codebase silently first.**

Before asking anything, spend time reading the project to form hypotheses:
- Scan the directory tree (2–3 levels deep).
- Read `CLAUDE.md` if it exists.
- Read a sample of source files across different directories to identify patterns.
- Note: what look like layers? what look like interfaces or contracts? what naming conventions appear? where does wiring/DI happen?

**2b. Run the architecture questionnaire.**

Ask the user the following questions. Present them all at once as a numbered list so the user can answer in one pass. Prefix each with what you observed, so the user can confirm, correct, or extend:

```
I explored the codebase and will now ask a few questions to lock down the architecture
before using it as an evaluation benchmark. Answer what you know — skip anything uncertain.

1. LAYERS
   I see the following candidate layers: [list what you found].
   Are these correct? Any to add, rename, or remove?

2. DEPENDENCY DIRECTION
   Which layers may depend on which? (e.g. "application → domain, infrastructure → domain")
   What crossings are explicitly forbidden?

3. INTERFACES / CONTRACTS
   I see these abstractions used as decoupling points: [list what you found — interfaces, abstract classes, ports, protocols].
   Are these the intended seams? Any missing?

4. NAMING VOCABULARY
   I see these suffixes/prefixes for project constructs: [list e.g. Service, Repository, UseCase, Gateway, Handler, Mapper].
   Is this the intended vocabulary? Any corrections?

5. WIRING / ASSEMBLY
   I see dependencies assembled in: [list what you found — DI container, factory, main class, etc.].
   Is that right?

6. ANYTHING ELSE
   Any architectural rule or constraint that isn't captured above and matters for code review?
   (e.g. "no static calls in domain", "all persistence goes through the Unit of Work", "events are the only cross-module communication")
```

**2c. Write `ARCH.md`.**

Using your observations and the user's answers, write `ARCH.md` in the project root with this structure:

```markdown
# Architecture

> Generated by /spec-workflow:spec-eval on <date>. Update this file when the architecture evolves.

## Layers

[Table or list: layer name | directory | responsibility]

## Dependency Direction

[Diagram or bullet list of allowed → directions and forbidden crossings]

## Interfaces & Contracts

[List of the abstractions used as seams between layers, where defined, where consumed]

## Naming Vocabulary

[Table: concept | suffix/prefix | example]

## Wiring & Assembly

[Where and how dependencies are composed]

## Additional Rules

[Any rules from question 6, or none]
```

**2d. Update the project's `CLAUDE.md`.**

Add a reference to `ARCH.md` near the top of the project's `CLAUDE.md` (create `CLAUDE.md` if it doesn't exist):

```markdown
## Architecture

See [ARCH.md](./ARCH.md) for the project's layer structure, dependency rules, interfaces, and naming vocabulary.
Use it as the benchmark when reviewing code quality or architectural fit.
```

**2e. Confirm with the user.**

Show the drafted `ARCH.md` and ask: *"Does this look right? Anything to correct before I save it and use it for the evaluation?"*

Apply corrections, then write the files. Then continue to Step 3.

---

## Step 3 — Take a deep breath

Before writing anything, pause and think carefully. This is a review, not a checklist race. Your goal is to surface real issues, not to validate work that might have subtle problems. Be honest and specific. You are measuring against *this project's* architecture — not a textbook.

---

## Step 4 — Evaluate along four axes

### A. Architectural fit

Using `ARCH.md` as the reference:

- Does each new class or module land in the right layer?
- Does it respect the dependency direction defined in `ARCH.md`? Or does it introduce a crossing that is forbidden?
- Does it use the project's existing interfaces/contracts — or bypass them and talk directly to a lower layer?
- Does it introduce a new pattern without justification (a new abstraction style, a new naming convention, a new wiring approach) inconsistent with the established vocabulary?
- If SOLID principles are relevant, apply them through the lens of the project's own layer design — e.g. "this class has two responsibilities *as defined by this project's conventions*", not in the abstract.

Name exact classes, methods, or files for each finding.

### B. Variable and identifier naming

Review every variable, method, field, constant, and class name introduced or modified in the diff. Ask:

- Is the name precise — does it say what it *is*, not how it's *used*?
- Is it consistent with the vocabulary defined in `ARCH.md`?
- Are there abbreviations that obscure meaning (`mgr`, `tmp`, `data`, `info`, `flag`)?
- Are booleans named as predicates (`isActive`, `hasPermission`)?
- Are collections named in plural, primitives in singular?
- Does the name reflect the correct layer (e.g. a domain concept named after an infrastructure detail, or vice versa)?

List any names that should be improved, with a suggested replacement and a one-line reason.

### C. Spec fidelity — does the implementation do what a reader would expect?

Re-read the spec's **Decision** and **Implementation** sections. Then ask:

- Would a developer reading the spec for the first time, then looking at this code, feel that it does exactly what was described?
- Are there behaviours in the code that the spec does not mention (scope creep or silent additions)?
- Are there things the spec calls for that the code doesn't do, or does differently in a way that matters?
- Are edge cases the spec implies handled in the code?
- Is the overall shape of the solution (layering, data flow, entry points) consistent with what the spec implies?

### D. Change division — conform to `CONTRIBUTING.md`

Check the branch's **commit and PR structure** against the project's `CONTRIBUTING.md`, to the letter. `CONTRIBUTING.md` is the only authority here — do **not** apply your own ideas of how a change should be split, and where it is silent on a point, say so rather than inventing a rule. (No `CONTRIBUTING.md` → skip this axis and note it.)

Inspect the *actual history*, not just the final diff: `git log --oneline main..HEAD`, what each commit contains, and whether the work is one PR or a stack. Then, for each dimension below, check **what `CONTRIBUTING.md` says** and whether the branch follows it:

- **Commit granularity**
- **Renames / moves**
- **Migrations** (e.g. separate PR? own commit? shipped with the model/code change?)
- **Enabling refactor vs behavior change**
- **What lands where** — the PR, a pre-PR, or a deferred follow-up
- …and any other change-division convention `CONTRIBUTING.md` documents.

For each divergence, **quote the `CONTRIBUTING.md` rule** it breaks and the structure that rule prescribes. Be proportionate — apply only what `CONTRIBUTING.md` actually requires. ✅ if the branch's division conforms.

## Step 5 — Write the evaluation report

Structure your output exactly like this:

---

## spec-eval: `<spec-slug>`

### Architecture Benchmark
[One line: "Using ARCH.md (bootstrapped this run)" or "Using existing ARCH.md". If bootstrapped, note any key decisions the user confirmed.]

### Architectural Fit
[For each finding: the class/file, what pattern it violates or diverges from, and why it matters. ✅ if no issues found.]

### Naming
[List of identifiers to reconsider, with suggested replacement and one-line reason. ✅ if naming is clean.]

### Spec Fidelity
[What matches, what diverges, what is missing, what was added without spec coverage.]

### Change Division
[One line naming the source: "Using CONTRIBUTING.md" or "CONTRIBUTING.md absent — not assessed". Then each divergence from its commit/PR conventions: the quoted rule, what the branch did, and the prescribed structure. ✅ if conformant.]

### Summary
[2–4 sentences: overall health of the implementation, the most important issue to address if any.]
