The shared format · html-doc

Four rules that make one file work everywhere

All three commands build on the html-doc skill, which encodes the non-obvious constraints so the outputs feel like one system.

Self-contained
Inline CSS/JS, no network, assets as data: URIs — renders as a local file, an email attachment, or a Claude Artifact under a strict CSP.
Theme-aware
Respects the reader's light/dark with a manual toggle. A document adapts to the reader — the opposite of a mockup.
Progressive disclosure
Conclusion visible, evidence one expand away via native <details>. Dense, but never a wall.
Visual evidence
The prose claim plus, when it helps, a supporting artifact under it — a code snippet, an inline-SVG diagram, a chart (via dataviz), a screenshot, or a layout sketch. Never the artifact alone.

How they work

Inside each tool

report · sources → a readable document

1

Frame first

It settles the audience and the angle — the one question the report is for — before gathering, so the result isn't an undifferentiated data dump.

2

Gather & cross-check

Pulls from whatever's present — repo & git, PRs, the issue tracker, docs & specs, logs — and cross-checks them. When two sources disagree, that discrepancy is itself a finding, surfaced rather than smoothed over.

/rich-html:report the state of the payments migration, for the team
3

Conclusion first

Leads with the answer; sections follow; every claim that rests on a source carries its proof one expand away, attributed so it's checkable. It never changes what it reports on.

decide · decisions → a surface + one prompt

1

Collect the pending choices

Sweeps for genuine forks: a concern's ## Options, unresolved PR-review forks, "needs decision" issues, autopilot escalations, TODO(decide:) markers. Not tasks — decisions.

2

Model each with real context

A one-line question, 2–4 concrete options (with a recommended one where the evidence supports it), and expandable context wired to the actual source — the point of the surface.

/rich-html:decide everything waiting on me across the open concerns and PRs
3

Emit one prompt

You choose per decision (or "accept all recommended"), and a Copy prompt button assembles a single, self-standing prompt — one line per decision with its choice and source — to hand straight back to an agent. It never degrades into chat Q&A.

branch-review · a diff → a filterable review

1

Resolve the diff

From a PR number/URL, a base...head range, a branch name, or bare — the current branch vs. its merge-base. The exact base and totals are pinned in the header, so you know precisely what's under review. Read-only.

2

Two filter axes

Every change is tagged by facet (code / tests / docs / spec) and clustered by change-type — why each cluster exists, named by its intent (jul2026-sync-replay, not a bare service). The full diff slices both ways, and a summary — files, ± lines, a dataviz chart — recomputes as you filter.

/rich-html:branch-review #662
3

Reasoning over hunks

Each cluster leads with one paragraph on why it exists; the real diff is one expand below it. The change-type rule was hardened by an adversarial redteam — the original seed-vs-emergent taxonomy became name-by-intent, with generic-layer naming as the checkable smell.

Which one

Reading, deciding, reviewing

Reaching for the state of something, a synthesis, a briefing → report. Facing a pile of unmade choices you want to clear in one pass → decide. Wanting to understand what a branch or PR changed, and why → branch-review. If report hits a decision that needs making it points at decide; if decide finds reportable state rather than a fork, it points back at report; and if a change hides an unmade decision, branch-review points at decide too.

branch-review — a third command (plugin 0.3.0)

Turns a branch or PR diff into a filterable HTML review: the full diff sliced by facet (code / tests / docs / spec) and regrouped by change-type, each cluster named by its intent rather than a generic layer. The change-type rule was hardened by an adversarial redteam across three real PRs — the original seed-vs-emergent taxonomy was undecidable when a change fit both, so it became name-by-intent with generic-layer naming as the checkable smell.
