Where should retry/backoff for outbound HTTP live?

A real fork parked in a PR thread: centralize the logic, or add it per call-site. The choice turns on how requests actually flow through the code.

Baselineprose evidence

Retry/backoff for outbound HTTP — centralize it, or per call-site?

  • Centralize in the client wrapperrecOne place; covers every call at once.
  • Add it per call-siteFlexible per call, but repeated and easy to forget.
Context — the two locations

Every outbound request already passes through a single request() function in the client wrapper, and that wrapper already exposes an interceptor hook. Putting backoff there would cover all 37 call sites at once. The per-call-site option repeats the logic and risks call sites that forget to add it.

Improvedprose + code

Retry/backoff for outbound HTTP — centralize it, or per call-site?

  • Centralize in the client wrapperrecOne place; covers every call at once.
  • Add it per call-siteFlexible per call, but repeated and easy to forget.
Context — the two locations

Every outbound request already passes through a single request() function, which already exposes an interceptor hook — so backoff added here covers all 37 call sites.

// client.ts:42 — every outbound call funnels through here
async function request(opts) {
  // ← backoff hook goes here: wraps all 37 call sites
  const res = await withRetry(() => fetch(opts.url, opts), policy);
  return res;
}

Path in: apiFor(x).get() → request() — no call site touches fetch directly.

What to look for. Axes 1 & 3 — with the snippet and the one-line path, can you commit to “centralize” without opening the repo? In Baseline you have to trust the sentence “everything funnels through request().”

Dashboard header — single-row toolbar, or split title and actions?

The form most likely to drift toward a mockup. The sketch has to stay a schematic thumbnail you choose against — not a facsimile of the product.

Baselineprose evidence

Dashboard header layout — one row, or title over actions?

  • Single row: title + 3 actions inlineCompact on desktop; actions wrap awkwardly under 768px.
  • Two rows: title, then actionsrecTaller, but stable on small screens.
Context — the two layouts

Option A keeps the title and the three action buttons on one line — compact on wide screens, but the buttons wrap under the title awkwardly below 768px. Option B gives the title its own row with the actions beneath it: one row taller, but it holds its shape at every width.
